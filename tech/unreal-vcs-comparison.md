# Unreal Engine プロジェクトの VCS 比較: Git、Perforce、LORE

新規 Unreal Engine プロジェクトで、アーティストと選定担当者が VCS を選ぶための比較。
特定の製品を標準と決めるものではなく、案件の規模、制作フロー、利用するバージョンに
応じた判断材料を示す。コードを含む一般的な比較は [VCS の選び方](vcs-selection.md)を参照。

> この資料の LORE の機能・対応状況は 2026 年 11 月時点の公開資料に基づく。
> LORE は開発中の製品であり、実際に採用する revision と Unreal Engine のバージョンで
> 確認する。社内の検証状況は [Lore ドキュメント](../lore/README.md)を参照。

## まず押さえたい違い

| 観点 | Git + Git LFS | Perforce Helix Core | LORE |
| --- | --- | --- | --- |
| 基本的な作業 | 編集後、ローカルで commit し、push で共有する | workspace で編集し、changelist を submit して共有する | 編集後、ローカルで commit し、push で共有する |
| アセットの競合 | LFS のロックを利用できる。サーバー・クライアントの対応を確認 | ファイル種別などに応じて排他編集を強制できる | ロックで編集中を知らせる。現行の公式 FAQ では強制しない |
| 大容量データ | LFS で大きなファイルの実体を Git の履歴と分けて管理できる | 大容量ファイルを扱い、workspace の対象範囲を絞れる | 断片単位の重複排除と必要に応じた取得を設計上の特徴とする |
| ブランチ・オフライン | ローカルで commit やブランチ操作ができる | 通常の submit はサーバーへの登録。オフライン作業には別途手順が必要 | ローカルで commit やブランチ操作ができる |
| 導入時の注目点 | LFS の容量・通信、ロック、GUI と CI の対応を検証 | サーバー、ライセンス、権限、workspace の運用を設計 | UE 連携、ロックの実効性、更新・復旧を対象 revision で検証 |

Git の列は、アセットを LFS で管理する構成を想定する。各機能を使えるかどうかだけでなく、
使用する GUI、Unreal Editor、サーバー、CI の組み合わせで期待どおり動くかを確認する。

## 比較の基準となる社内の Perforce 運用

現在は `helix-p4d → helix-proxy → 開発者` の構成を使っている。プロキシはファイルの
取得を支えるキャッシュであり、履歴や権限を管理するサーバーの代わりではない。

制作は **main ストリームを中心**に進め、試したいことがある場合に feature ストリームを
使い、結果を最終的に main に戻してきた。新規案件の比較では、この作業の流れと
プロキシを含む取得環境を Perforce の基準とする。

以前は Git と Git LFS のロックを使い、デザイナーがファイルをロックしていた。
その運用ではロックがブランチを横断し、別ブランチで同じアセットを並行して編集しにくかった。
Git のブランチ機能が使えないのではなく、アセットの排他とブランチを併用すると
並行制作が制約される、という経験である。

その後、Git の環境に SVN を設けて動作を確認し、アセットデータは SVN、
プログラムソースは Git で管理する構成を採用した。これは Git LFS でアセットを管理する
構成とは別の選択肢であり、比較表の Git + LFS と区別する。

## 制作中に何が変わるか

### 自分の変更を残し、チームに共有する

- **Git / LORE**: ローカル commit で作業の節目を記録し、push して他の人に共有する。
  push 前の変更は通常その端末にしかなく、端末の故障に備えたバックアップとは限らない。
- **Perforce**: 編集対象を open し、関連する変更を changelist にまとめて submit する。
  submit 前でも shelve により変更をサーバーに一時保存・共有できるが、submit や
  ローカル commit とは別の操作である。

いずれも、アーティストが「保存」「履歴への記録」「他の人への共有」を区別できるよう、
実際に使う Editor と GUI の操作を確認する。

### 同じアセットを複数人が編集する

`.uasset` や `.umap` のようなファイルは、一般的なテキストのように行単位でマージできる
とは限らない。ロックは衝突を減らす手段であり、競合が起きた後の解決手順も必要になる。

- **Git + LFS**: LFS のロックを利用できるが、利用するサーバーやクライアントが対応し、
  チームの操作でロックを尊重できるか確認する。社内の以前の運用ではロックがブランチを
  横断し、同じパスのアセットを別ブランチで同時に扱う際の制約になった。
- **Perforce**: 対象ファイルを排他編集にする設定を利用できる。すべてのファイルが
  自動的に排他になるわけではなく、ファイル種別や運用の設計が必要。
- **LORE**: 公式 FAQ ではロックは注意喚起型で、他者の操作を強制的に止めないと説明される。
  誰が編集中かを確認し、担当を調整する運用が必要。対象 revision と Editor での表示を確認する。

強制的な排他が必須かは案件次第。担当範囲の分担や確認ルールで回るチームもあれば、
多数の制作者や複数ブランチを扱うため、強制が重要なチームもある。Unreal の
One File Per Actor などで競合の範囲を分けられる場合もあるが、すべての競合がなくなるわけではない。

### 大量のデータを取得する

LORE はファイルを断片に分け、同じ内容の重複を減らし、必要なデータを遅延取得する設計である。
Git LFS は大きなファイルの実体を別途管理し、Perforce は workspace の対象を絞って取得できる。

社内で採用した Git + SVN の構成では、プログラムとアセットの履歴が別々になる。
新規案件で同じ構成を検討する際は、動作する組み合わせをどう記録し、制作者や CI が
対応する両方のバージョンをどう取得するかも確認する。

いずれも構成次第で取得量を減らせるが、**必ず LORE が最速・最安という意味ではない**。
実際のアセットの変更内容、取得範囲、ネットワーク、キャッシュ、サーバー構成によって結果は変わる。
必要なファイルが手元にない状態では、オフライン中に追加取得できない点にも注意する。

### 別案を試す

現在の Perforce 運用では、main ストリームで普段の開発を続け、必要に応じて feature
ストリームで別案を試し、変更を main に戻す。

LORE と Git でも、main に相当するブランチから作業用ブランチを作り、変更を積んでから
main にマージする流れを組める。ただし、Perforce Streams とブランチは同一の仕組みではない。
作成・切り替え・共有・統合の操作や権限、レビューの方法をそれぞれ確認する。LORE と Git は
ローカルで commit できるため、共有前に作業の節目を記録することもできる。

どの製品でも、同じバイナリアセットを別々に変更した後の統合は自動で解決できるとは限らない。
別案を作る手軽さだけでなく、どの案を採用し、競合をどう解決するかまで試す。

例えば main でデザイナーがアセットをロックしている間、別のデザイナーが feature ブランチで
同じアセットを試したい場合、以前の社内 Git LFS 運用ではブランチを分けてもロックが影響した。
ロックの確認、解除、編集や push の可否は利用する LFS サーバーとクライアントで確認する。

LORE はロックが注意喚起型であり、ブランチを分けた場合の表示やロック取得の挙動も
対象 revision で検証する。Perforce についても、現在の Streams とファイル種別の設定で
同じシナリオを試す。どちらも、並行編集できることと main への統合が容易であることは別問題である。

## Unreal Editor・CI との連携

Unreal Editor の画面からアセットの状態確認、編集開始、変更の共有、履歴の確認までを
実際に試す。ツールによっては、一部の操作に別の GUI や CLI が必要になる。
Git を使う場合は、選択する Editor 連携と GUI が LFS やロックにどう対応するかを確認する。

LORE の Unreal Editor プラグインは、[公式チュートリアル](https://epicgames.github.io/lore/tutorials/getting-started-with-lore-for-unreal-editor/)では
UE 5.9 Preview 1 以降の experimental とされている。使用予定の UE と LORE の組み合わせで
利用できるか、必要な操作が完結するかを検証する。experimental を本番で許容するかは
案件ごとに判断する。

CI では、必要な revision とアセットを取得できることに加え、認証情報の管理、
ビルド環境の再現性、取得時間、容量、失敗時の通知を確認する。

## 費用と運用

- **Git + LFS**: Git と LFS はオープンソース。ホスティング、LFS の保存・転送量、
  GUI や CI の利用には選択したサービスに応じて費用がかかり得る。
- **Perforce**: 自己ホストや提供サービス、利用者数などに応じたライセンス・費用を確認する。
  サーバーの設置・管理を自社で行うかどうかも総費用に影響する。
- **LORE**: 本体は MIT ライセンスで、ライセンス料なしで利用できる。サーバー、
  ストレージ、通信、認証、運用・保守は別途必要。デスクトップクライアントのライセンスは
  本体と同一とは限らないため、利用する製品ごとに確認する。

契約条件や料金は変わるため、選定時に公式情報と見積もりを確認する。3 製品とも、
バックアップの取得だけでなく、復元試験、アクセス権、監視、更新担当を含めて見積もる。
社内の LORE 認証・権限連携には検証実績がある一方、バックアップ復元やチーム運用の
確認は別途必要である。

## 案件ごとの判断材料

| 案件で重視すること | 検討の方向 |
| --- | --- |
| コード中心で、既存の Git レビュー・CI を生かしたい | Git + LFS を検討。アーティストの操作とアセット量を検証する |
| 強制的な排他編集と、確立された制作運用を重視 | Perforce を基準に検討。対象ファイルの設定と費用を確認する |
| 大規模コンテンツとローカル履歴を両立したい | LORE を検討。注意喚起型ロック、UE 連携、運用の成熟度を評価する |
| 注意喚起型のロックで制作できるか判断がつかない | 実際の担当分担、ブランチ、競合時の対処を含めて試す |

これらは選定の出発点であり、案件の規模だけで自動的に製品を決めるものではない。

## 採用前に試すこと

実際のプロジェクトに近いアセットと、アーティストを含む参加者で小規模に検証する。
最初にデータ量、ネットワーク、端末、対象バージョン、許容時間・費用を決め、
同じ条件で結果を比較する。

1. **日常作業**: Editor や GUI から取得、編集、変更確認、共有、履歴確認を行い、
   必要な手順と迷いやすい点を記録する。
2. **競合とロック**: 2 人が同じアセットを編集し、同一・別ブランチでの表示、警告、
   編集・共有の可否と、競合後の復旧手順を確認する。
3. **データ量と速度**: 初回取得、更新、ブランチ切り替えの所要時間と転送量、
   クライアント・サーバーの使用容量を測る。Perforce は既存の proxy を含む構成を
   基準とし、各製品のキャッシュやネットワーク条件も記録する。
4. **オフラインと別案**: 通信断の前後で、手元にあるファイルの編集・履歴記録と、
   未取得ファイルやロック情報の扱いを試す。main で開発を続けながら別案を試し、
   変更を main に戻す一連の流れも確認する。
5. **Editor・CI**: 対象 UE バージョンで必要な操作を試し、CI が必要なアセットを取得して
   ビルドできることを確認する。
6. **費用・復旧**: 利用者数、保存量、転送量、運用工数を基に見積もり、バックアップからの
   復元を隔離環境で試す。

結果は「できた／できない」だけでなく、必要な手動作業、制限、失敗時の影響も残す。
