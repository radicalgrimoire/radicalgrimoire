# VCS の選び方: Perforce、LORE、Git、Plastic SCM

VCS は「どれが最強か」ではなく、扱うデータ、チームの作業場所、そして衝突をどう扱いたいかで選ぶ。特にゲーム開発では、ソースコードと巨大なバイナリを同じ感覚で扱わないことが重要になる。

この記事でいう Plastic SCM は、現在 Unity Version Control として提供されている製品を指す。

## まず比較

| VCS | 方式 | 得意なこと | 注意したいこと |
| --- | --- | --- | --- |
| Perforce Helix Core | 中央集権型 | 大容量バイナリ、厳格な権限、排他ロック、既存のゲーム制作フロー | サーバー運用とライセンスを前提に考える必要がある |
| LORE | 分散型＋中央サービス | 大規模コンテンツの遅延取得、オフライン作業、モダンなゲーム向けデータ管理 | まだ新しく、導入実績・周辺ツール・運用ノウハウは事前に検証したい |
| Git | 分散型 | ソースコード、ブランチを多用する開発、ホスティングや CI との連携 | 巨大なバイナリや頻繁に更新するアセットは、そのままでは扱いづらい |
| Plastic SCM / Unity Version Control | 集中・分散の両方に対応 | Unity を中心とした開発、GUI を使ったブランチ・マージ、バイナリとコードの混在 | Unity 外での運用や、必要なエディション・ホスティング形態を確認する |

## 向いているチーム

### Perforce Helix Core

Unreal Engine のプロジェクト、映像・音声・DCC データを大量に扱うチーム、または「このファイルは一人だけが編集する」と明確に制御したいチームに向く。パス単位の権限、ワークスペース、Streams、ロックといった中央管理の仕組みが強い。

その代わり、サーバーのバックアップ、アップグレード、権限設計を担当できる人は必要になる。大人数の制作現場で運用を固められるなら、有力な選択肢である。

### LORE

LORE は、ローカルで commit やブランチ操作を進めつつ、必要なデータだけを取得する設計が特徴である。巨大なコンテンツを持つゲーム開発で、Git の操作感に近い分散ワークフローを求める場合に検討しやすい。

一方で、新しい製品を採用するなら、ロック運用、認証、バックアップ、CI、チームが使う DCC・ゲームエンジン連携まで小さな検証環境で確認したい。Perforce の既存運用をそのまま置き換えられるとは限らない。

### Git

アプリケーションやツール、テキスト中心のソースコードには、まず Git が基準になる。GitHub や GitLab、CI、コードレビュー、IDE との統合が成熟しており、開発者の学習コストも比較的低い。

ただし、数 GB 級のバイナリを頻繁に更新する用途は慎重に扱う。Git LFS で補える場面はあるが、ロック、取得範囲、履歴の増え方を含め、アセット制作の主リポジトリとして適するかは別途判断する。

### Plastic SCM / Unity Version Control

Unity を利用するチームで、Git よりアセット管理を意識した GUI とワークフローを求める場合の候補になる。コードとバイナリが混在するプロジェクトで、ブランチやマージを開発者以外にも扱いやすくしたいときに検討しやすい。

採用前には、利用する Unity のバージョン、クラウドか自己ホストか、外部ツールとの連携、料金と権限管理を確認する。Unity を使わない組織でも利用は可能だが、比較対象に対する優位性を実プロジェクトで試すべきである。

## 迷ったときの目安

- **コード中心で、一般的な開発基盤を早く整えたい**: Git
- **巨大なアセットと排他編集を確実に運用したい**: Perforce Helix Core
- **巨大なコンテンツを分散型ワークフローで扱いたい**: LORE
- **Unity プロジェクトで、アセットとコードをまとめて扱いたい**: Unity Version Control

最終判断は、機能表だけではしないほうがよい。実際のプロジェクトから、巨大なアセット、同時編集しやすいファイル、リリースブランチを含む小さなサンプルを作り、clone／sync の時間、衝突時の手順、権限・ロック、バックアップ復元を試すと失敗しにくい。
