# VCS の選び方: Git、Perforce、LORE

VCS は「どれが最強か」ではなく、扱うデータ、チームの作業場所、そして衝突をどう扱いたいかで選ぶ。特にゲーム開発では、ソースコードと巨大なバイナリを同じ感覚で扱わないことが重要になる。

社内での Perforce 運用を基準に、新規案件の選択肢として LORE と Git を比較する。

## 向いているチーム

### Git

アプリケーションやツール、テキスト中心のソースコードには、まず Git が基準になる。GitHub や GitLab、CI、コードレビュー、IDE との統合が成熟しており、開発者の学習コストも比較的低い。

大きなアセットも、Git の拡張機能である Git LFS を使えばコミットして管理できる。
Git LFS は、Git の履歴にはファイルの参照情報を記録し、ファイルの実体は別のストレージに保存する仕組みである。

Git 自体には、アセットの同時編集を防ぐファイルロック機能はないが、
Git LFS を使うとファイルをロックできる。

ただし、Git LFS のロックはリポジトリ内の同じパスに対してブランチを横断して適用される。
そのため、あるブランチでロックされたアセットを、別のブランチで並行して編集することが
できなかった。

Git のブランチ自体は利用できるが、ロックを活用するアセット制作では、
ブランチを分けても自由に並行作業できるとは限らない。

この課題に対し、社内では Git の環境に SVN を設けて動作を確認し、アセットデータを SVN、
プログラムソースを Git で管理する構成を採用した。コードとアセットの履歴が分かれるため、
新規案件で同様の構成を使う場合は、対応するバージョンの組み合わせや CI での取得を確認する。

こうして、コードとアセットで二つのバージョン管理を使い分ける、
誰もが苦しむ地獄の開発環境が爆誕した。

### Perforce Helix Core

Perforce を活用した理由の一つは、Git LFS で課題になったファイルロックである。
main と feature がそれぞれ別のファイルを持つ構成では、片方のストリームでロックしても、
もう片方のファイルはロックされない。ブランチを分けてアセットを並行して試せる。
ただし、同じファイルを複数のストリームから参照する構成では、ロックの影響も共有される。

さらに、大量のデータを高速に取得でき、GUI による操作環境もあった。
Epic Games が Perforce から Unreal Engine のプロジェクトを取得する
[UnrealGameSync](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-game-sync-ugs-for-unreal-engine) を
開発していたこともあり、Unreal Engine との親和性があった。

シングルサインオンにも対応しており、社内ではコロナ禍の遠隔作業において、
認証を一元化し、セキュリティを確保するうえで役立った。

その一方で、インフラの構築・運用負担はかなり大きかった。
当時は Git のホスティングサービスのように気軽に使い始められる環境がなく、
サーバーの構築から、バックアップ、アップグレード、権限設計まで学んで用意する必要があった。

例えば、外部の会社には特定のファイルパスだけを見せ、それ以外は見せない。
さらに、見せる範囲も取得だけを許可し、変更は許可しない。
こうした要求に合わせて、誰がどの範囲にアクセスできるかを設計する必要がある。

また、A さんは特定のアセットを取得したいが、B さんには不要という場合もある。
不要なデータまで取得すると時間も容量もかかるため、それぞれの作業に必要な範囲を
ワークスペースで選べるようにする。これはアクセス権の制限とは別の設定である。

現在のような生成 AI に相談できる時代でもなかったため、調査も一から進める必要があった。

### LORE

LORE は、Epic Games が開発した新しいバージョン管理システムである。
コードと大容量のアセットを一緒に扱うことを想定しており、
Git LFS のような別の拡張機能を使わずに管理できる。

ファイルを小さな単位に分け、同じ内容を重複して保存しない仕組みを持つ。
また、取得する範囲を絞れるため、必要のないアセットをすべて手元に置く必要はない。

Git のようにローカルでコミットやブランチの作成ができ、
通信できない間も手元にあるデータを使って作業を進められる。
チームへの共有には push が必要である。

LORE 本体は MIT ライセンスのオープンソースであり、ライセンス料なしで利用できる。
ただし、サーバーやストレージの費用、構築・運用の負担は別途必要になる。

ファイルロックも利用できるが、現時点では編集中であることを知らせるためのもので、
他の人の編集を強制的に止めるものではない。

最大の問題は、LORE 自体に認証基盤がなく、チームで利用するには別途用意する必要があることだ。
この問題に対応するため、[lore-auth-bridge](https://github.com/radicalgrimoire/lore-auth-bridge) を
開発し、シングルサインオンに対応した。

また、公式の GUI ツールは存在するものの、現状では使い勝手が悪く、
実用的な GUI が十分に整っているとは言い難い。

### lore-auth-bridge でできること

- Microsoft Entra ID と連携し、シングルサインオンでログインする。
- ユーザーやグループを管理し、リポジトリごとに読み取り・書き込み・管理の権限を設定する。
- CI などの自動処理に、サービスアカウントを利用する。
- 管理用 CLI や、必要に応じて有効にする Web UI からユーザーや権限を管理する。
- 認証・権限管理に関わる操作の監査記録を残す。

Entra ID のユーザー識別にはオブジェクト ID を利用する。
一度退職などでアカウントが削除され、復帰時に再作成された場合は、
同じ人やメールアドレスであっても別のアカウントとして扱う。
以前の権限は自動で引き継がず、管理者が新しいアカウントを登録する必要がある。

権限管理はリポジトリ単位であり、ファイルごとのロックを強制する機能ではない。
構築や運用の詳細は [Lore ドキュメント](../lore/README.md)を参照する。
