# LORE 社内環境の再現性に関する検討

## 背景

215 はアシスタントに構築を任せ、216 はアシスタントの案内に従って手動で構築した。両環境には Nginx の設定などに差があり、同じ目的の環境を再現するための共通の基準が必要になった。

`lore-auth.yaml.md` は設定を表示した時点の端末記録であり、現在の実機設定と一致するとは限らない。また、端末の入力・プロンプトを含むため、そのまま設定ファイルとしては使えない。

## 現時点の方針

- LORE は Docker 管理を前提とせず、Ubuntu 上でネイティブに動かす。
- Ubuntu 上で Ansible を使い、構成を定義して同じ設計の環境を再現する方向で検討する。
- 社内利用を前提とする。Nginx は主に OIDC のブラウザ認証・callback に必要な HTTPS を提供するために使用する。
- Nginx はひとまず 215 の設定を基準とする。215 と 216 の値の違いや必要な変更は、実設定を確認してから整理する。
- `/datadrive` のディスク作成やマウント設定は LORE 構築の対象外とし、準備済みの前提条件として扱う。
- 現在の記録は作業履歴として残し、共通の構成定義、サーバー固有の値、実機への適用・検証結果を区別する。

## 明日以降の検討事項

1. Ansible を実行する Ubuntu と、215・216 への接続方法を決める。
2. 215・216 の実設定を棚卸しし、環境固有の値、共通化する設定、未決定事項に分類する。
3. LORE CLI、loreserver、lore-auth-bridge、Nginx、systemd の構成定義と、環境別の値の持ち方を決める。
4. ソースの commit、Rust、依存パッケージ、Ansible のバージョンをどの範囲まで固定するか決める。
5. Nginx の 215 ベースの設定を確認し、HTTP・gRPC の接続元 IP の扱い、ReBAC の許可範囲、ログ、証明書検証を整理する。
6. 初回構築と既存環境の更新を分け、DB、リポジトリデータ、証明書、秘密鍵を再実行時に上書き・再生成しない方法を決める。
7. Entra の client secret や署名鍵などの安全な管理方法を決める。secret・トークン・秘密鍵の値は構成定義や作業記録に含めない。
8. 社内向けのユーザー登録は招待ではなく、アカウント追加と Entra identity の直接紐付けを基本とする。216 に作成済みの pending 招待の扱いは別途確認する。
9. 既存の 215・216 に適用する前に、安全に現状との差を確認する手順と、適用後のサービス・認証・CLI・リポジトリ操作の検証手順を用意する。
10. 社外公開が必要になった場合は Azure Application Gateway を入口とする想定で、別途通信方式や認証 URL を検討する。今回の社内構築に必要な設定とは分ける。

## 注意

- Ansible の `--check` は事前確認に役立つが、すべての操作を正確に予測するものではない。タスクの設定によっては check mode 中でも実行されるものがある。
- `--diff` やログに secret が出ないようにする。
- `lore-auth.yaml.md` には組織の設定情報やメールアドレスが含まれるため、共有やコミットの前に内容と公開範囲を確認する。
- Ansible を導入するだけでは完全な再現性は保証されない。パッケージの取得元やバージョン、既存データ、証明書、外部 IdP の設定も考慮する。
- 既存環境への適用、サービス再起動、データ変更は、内容と影響を確認してから行う。
